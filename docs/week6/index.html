What I learned

design

Describe your design: hypervisors, tenants, VNIs and addresses. Which tenants overlap, and why did you place each VM where you did?

A four-rack data centre on my block 10.3.0.0/16. The racks rack1 to rack4 are the hypervisors, at 10.3.0.1 to 10.3.0.4 on the underlay 10.3.0.0/24. The underlay MTU is 9000, my chosen fix. The VNIs come from my ID: 4901, 4902 and 4903.

Two of your VMs have the same IP address. Using your evidence, explain how a ping reaches the right one — and what would have to go wrong for one tenant to see another's traffic.

web2 (shop, rack2) and pay2 (bank, rack3) are both 10.3.50.11. From isolation.txt:

How the right VM is reached:

  • The sender's port decides the tenant. web1's port is in br4901, pay1's port is in br4902.
  • Each bridge has only its own VXLAN device, so the frame leaves rack1 tagged with VNI 4901 or 4902.
  • rack3 did receive shop's flooded ARP (flood.txt), but it decapsulated it into vxlan4901 → br4901. That bridge holds only web3's port. pay2's port, rack3-eth2, is in br4902, so pay2 never saw it.
  • The overlay never looks at the IP address: the same IP gives two different MACs, one per VNI.

What would have to go wrong for one tenant to see another's traffic:

  • A VM port in the wrong bridge, for example rack3-eth2 master br4901 from an off-by-one in the port numbers.
  • Two tenants given the same VNI (check_spec() refuses that), or a VXLAN device created with the wrong id.
  • An attack on the underlay. VXLAN has no authentication or encryption, so anyone who can send UDP to port 4789 on a rack could inject VNI 4902 frames into bank. The underlay must be trusted, or protected with IPsec or MACsec.
flood learn

Using your evidence, explain what was flooded, to which hypervisors, and what each VTEP learned. With 50 hypervisors in one VNI, how many copies would one broadcast need — and how would EVPN change that?

web1 pinged web2 (10.3.50.11). The only frame flooded was web1's ARP broadcast "who-has 10.3.50.11". rack1's vxlan4901 copied it once to each entry in its flood list (head-end replication). The ARP reply and the ICMP echoes were unicast, because by then the MACs were known.

rack4not in VNI 4901no: 0 packets captured—
  • A VTEP learns from the outer source IP of every packet it receives, even a flood. That is why rack3 learned web1.
  • Learned entries are not permanent, so they age out. The flood entries my code created stay.

With 50 hypervisors in one VNI, every broadcast or unknown-unicast frame needs 49 copies, and every flood list has 49 entries to maintain by hand. EVPN (a BGP control plane) changes that:

  • Type 3 routes build the flood lists automatically, replacing my bridge fdb append lines.
  • Type 2 routes advertise each VM's MAC and IP when it starts, so every VTEP knows where each MAC is before any traffic. No data-plane learning is needed.
  • ARP suppression: the local VTEP answers ARP from that table, so most broadcasts never leave the hypervisor. A real broadcast still costs 49 copies unless the underlay does multicast, but such broadcasts become rare.

p4

If your hypervisors' VTEPs were P4 switches running the lecture's vtep.p4, what would have to fill the vtep_encap table, and how? What would replace flood-and-learn?

Who fills it: in vtep.p4 both tables start empty and default to drop. A P4 program cannot write its own tables, so the control plane must fill them, as in the Week 5 lab (P4Runtime, or simple_switch_CLI table_add).

How: vtep_encap is keyed on (ingress port, destination MAC). The port identifies the tenant, because each VM has its own port. The encap action is given the VNI, the switch's own MAC and VTEP address, the remote VTEP, the next-hop MAC on the underlay, and the output port. vtep_decap is keyed on (VNI, inner destination MAC). For my rack1 (port 1 = web1, shop; port 2 = pay1, bank):

TableKeyActionReaches
vtep_encapport 1, 02:00:13:25:00:0bencap(4901, …, 10.3.0.1 → 10.3.0.2, …)web2
vtep_encapport 1, 02:00:13:25:00:0cencap(4901, …, 10.3.0.1 → 10.3.0.3, …)web3
vtep_encapport 2, 02:00:13:26:00:0bencap(4902, …, 10.3.0.1 → 10.3.0.3, …)pay2
vtep_decap4901, 02:00:13:25:00:0adecap(port 1)web1
vtep_decap4902, 02:00:13:26:00:0adecap(port 2)pay1
  • web1 and pay1 share 10.3.50.10 but never collide: the keys use port, MAC and VNI, never the IP address.
  • My overlay.yaml already holds everything needed. plan() gives every VM's MAC, VNI and hypervisor, and vm_ports() gives each VM's port, so a controller could generate these entries the same way all_commands() generates my ip and bridge commands.

What replaces flood-and-learn: a control plane that knows every VM in advance, either the orchestrator's inventory or EVPN type 2 routes turned into table entries.

  • vtep.p4 cannot learn and has no flooding, so a frame for an unknown MAC is dropped, not flooded.
  • It has no ARP either, so the controller must answer ARP or the VMs must have static neighbour entries.
  • Cost: every VM must be installed before it can talk. Gain: no floods at all, and no 49-copy broadcasts.
